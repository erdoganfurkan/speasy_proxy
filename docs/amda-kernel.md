# Serving AMDA_Kernel from this proxy

This branch adds one endpoint, `/metadata`, so that `amdaXMLRequestorTool` can read
parameters through speasy. Everything else it needs was already here.

## What the kernel already speaks

`SpeasyProxyRequest::getSpeasyProxyLink()` builds

```
GET /get_data?path=<uid>&start_time=<iso>&stop_time=<iso>&format=cdf&zstd_compression=false&pickle_proto=3
```

which is this proxy's `/get_data` contract, unchanged. The kernel needs no patch to talk
to it.

## What `/metadata` adds

```
GET /metadata?path=archive/ddbase/ace_imf_all/IMF

TYPE=DOUBLE
DIM1=3
DIM2=1
MIN_SAMPLING=16.0
```

`GetVIWithSpeasyNode.cc` scans the body for those four keys and falls back on its own
defaults (`DOUBLE`, `1`, `1`, `1.0`) for any it does not find, and it ignores the HTTP
status. So a key the inventory cannot answer is omitted rather than guessed, and an
unknown product answers 404 with an empty body.

Nothing is downloaded: the answer comes from the speasy inventory. `spz_shape` and
`cdf_type` sit on the `ParameterIndex`, `MinSampling` on the dataset — for a direct
archive it reaches there through the YAML entry's `meta:` block, which
`amda-ddbase-yaml` fills from DDBASE's own `<vi>_info.nc`.

A provider that declares no `MinSampling` therefore leaves that line out and the kernel
uses its 1.0 s default. That is not a case that arises today: `/metadata` has exactly one
caller, `GetVIWithSpeasyNode.cc`, which serves `<vi serverMode='speasy'>` nodes, and the
other speasy route (`GetSpeasyProxyNode.cc`, used for `cda/...` UIDs) reads
`minSampling`, `dim1` and `type` straight off its own XML instead of asking here.

`/get_inventory` carries the same information, but a whole provider per call. The kernel
asks once per parameter, from C++, over curl.

## Running it for AMDA

The chain `AMDA_Kernel -> speasy -> netCDF codec -> PyISTP -> DDBASE` needs the forks,
not the PyPI releases:

```
speasy @ git+https://github.com/erdoganfurkan/speasy.git@<branch>
pyistp @ git+https://github.com/erdoganfurkan/PyISTP.git@main
```

The DDBASE inventory is a direct-archive YAML generated by `amda-ddbase-yaml`, installed
as `~/.config/speasy/archive/ddbase.yaml`. It holds **absolute paths**, so regenerate it
per environment (`$DDSYS_XML`, `$DDBASE_DATA_ROOT`) rather than copying it between
machines.

Point the kernel at the port this proxy listens on with `app.speasyproxy.url` in
`app.properties`.

### Startup time

The app builds every enabled provider's inventory during startup, before it serves
anything, and several providers fetch their catalogue over the network. With `archive`
alone the port answers immediately; with `cda` on it takes minutes — and if CDAWeb's
catalogue host is slow or unreachable it does not just take longer, it **retries until it
gives up**, so the port never opens at all (measured: 6 min 40 with no answer, urllib3
retrying `spdf.gsfc.nasa.gov/pub/catalogs/all.xml`). `astroquery`'s TAP logs during that
window make it look busy rather than stuck.

```
SPEASY_CORE_DISABLED_PROVIDERS="amda,csa,ssc,uiowaephtool,cdpp3dview"
```

Whether to keep `cda` is a real trade-off, not a detail. The kernel has a single
`app.speasyproxy.url`, so this instance also serves the `cda/...` UIDs that parameters
like `imf_speasy_cda.xml` ask for. Disable it and DDBASE works instantly but those
parameters return nothing; enable it and startup depends on CDAWeb being reachable. For
DDBASE work, disable it.

## Not here yet

`DEPEND` axis tables for spectrograms, and parameters with three dimensions past the
time axis. Both are kernel-side work (`GetVIWithSpeasyNode.cc`), tracked as #12813 and
#12814; `/metadata` will need to describe the axes once that lands.
